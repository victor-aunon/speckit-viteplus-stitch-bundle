# FEATURE: JWT Token Verification & Claims Extractor Service

## 1. Context & Purpose
Provide a decoupled, high-performance backend authentication service to validate JWT tokens, extract identity claims (userId, tenantId, roles, permissions), and verify cryptographic signatures in authenticated microservices without relying on UI dependencies or external web frameworks.

## 2. Domain Entities & Value Objects
- TokenPayload: Immutable domain entity containing userId (UUID), tenantId (string), roles (string array), and permissions (string array).
- TokenExpiry: Value object validating the temporal validity window (issuedAt, expiresAt) and expiration status.
- VerificationResult: Discriminated union result (Success with UserClaims vs Failure with AuthErrorReason).

## 3. Application Services & Ports
- TokenVerifierPort (Output Port): Cryptographic abstraction contract for signature verification and payload decoding.
- VerifyTokenUseCase (Application Service): Orchestrates token verification, validates temporal expiration, and maps to the domain entity.
- JwtService (Infrastructure Adapter): Implementation of TokenVerifierPort using crypto/jsonwebtoken with centralized JWT_SECRET configuration.

## 4. Key Acceptance Criteria (Gherkin Scenarios)
- Scenario 1 (Valid token with complete claims):
  Given a JWT token correctly signed with JWT_SECRET and a future expiration timestamp
  When VerifyTokenUseCase processes the token
  Then it returns VerificationResult with status 'success' and typed user claims (userId, tenantId, roles).

- Scenario 2 (Expired token):
  Given a JWT token with an 'exp' timestamp in the past
  When VerifyTokenUseCase evaluates token expiration
  Then it immediately rejects the operation returning status 'expired' without querying external storage.

- Scenario 3 (Invalid signature or tampered payload):
  Given a tampered token or one signed with an incorrect secret key
  When VerifyTokenUseCase attempts cryptographic verification
  Then it returns status 'invalid_signature' and logs a structured security audit event.

## 5. Technical Constraints & Quality Gates
- Strict Clean Architecture with vertical slices under src/features/auth/ (domain, application, infrastructure).
- The domain layer MUST NOT import infrastructure, third-party libraries, or unnecessary Node built-ins.
- Centralized environment variable access (JWT_SECRET, JWT_ISSUER) strictly via src/config/env.ts.
- has_ui=false: Zero dependencies on React, Vite visual gates, Playwright, or Tailwind.
- 100% unit test coverage for VerifyTokenUseCase and TokenExpiry.
